可以。按迭代方式，我建议不要一次性把 `python-backend` 改成“大平台”，而是分成 8 个可验收版本。核心思路是：先把现有能力稳住，再抽象 Prompt / Skill / Memory / Workflow，最后再把多 Agent、任务编排、音频音乐、质量评估完整接进去。

我这里按 `python-backend` 作为升级目标，同时保留现有前端和 API 兼容性来设计。

## 迭代 0：安全与工程底座修复

目标：先保证后续升级不会建在脆弱基础上。

改造内容：

- 配置改造：数据库密码、AI Key、存储路径全部从环境变量或密钥配置读取。
- AI Key 加密/脱敏：接口返回不再暴露明文 Key。
- 增加基础鉴权：本地模式可关闭，部署模式必须启用。
- 上传安全：限制文件类型、大小、路径穿越、图片/音频/视频 MIME 校验。
- 日志修复：当前大量 `extra` 字段应进入结构化日志，方便追踪任务。
- 增加统一错误码：AI 调用失败、JSON 解析失败、任务失败、素材下载失败要可区分。

交付结果：

- 配置安全化。
- 日志可按 `drama_id`、`episode_id`、`task_id`、`agent_run_id` 查询。
- 不改变现有业务流程。

验收标准：

- 原有接口兼容。
- 无明文密钥返回。
- 上传恶意路径、超大文件、错误 MIME 会被拒绝。

## 迭代 1：结构化数据模型与脚本标准

目标：先把“剧本、角色、场景、道具、分镜、声音、音乐”定义清楚，否则 Agent 很难协作。

新增核心 Schema：

- `ScriptSpec`：剧本创作要求。
- `NovelAdaptationSpec`：小说改编要求。
- `DramaBible`：整部剧设定。
- `EpisodeScript`：单集剧本。
- `CharacterProfile`：角色人设。
- `SceneProfile`：场景设定。
- `PropProfile`：道具设定。
- `StoryboardShot`：分镜。
- `VisualPrompt`：文生图提示词。
- `VideoPrompt`：图生视频提示词。
- `VoiceProfile`：角色声音设定。
- `MusicBible`：整剧音乐设定。
- `MusicCue`：单场景/单分镜音乐提示。

两类剧本入口要分开：

| 类型 | 特点 | 必须补充的结构 |
|---|---|---|
| AI 原创剧本 | 要求更重，必须先理解创作目标 | 类型、受众、平台、集数、时长、爆点、冲突密度、禁忌、风格参考 |
| 小说转剧本 | 要保留原著一致性 | 章节索引、原文摘要、人物关系、世界观、改编策略、保留/删改清单 |

交付结果：

- 所有 AI 输出尽量变成 Pydantic 结构化对象。
- 当前散落的 JSON 解析逻辑逐步统一。
- 后续 Agent 输出有稳定输入/输出契约。

验收标准：

- AI 原创能生成符合结构的剧本。
- 小说导入后能生成章节摘要、人物关系、改编计划。
- JSON 解析失败时可以自动修复或明确失败原因。

## 迭代 2：Prompt、Skill、Context 统一中心

目标：解决“提示词散落、上下文不可控、升级难回滚”的问题。

建议不要把 Prompt 完全分散在各 Agent 内。Agent 只声明自己要做什么，真正的 Prompt、上下文、版本、模型策略由平台统一管理。

新增模块：

```text
app/prompts/
  registry_service.py
  renderer.py
  templates/

app/skills/
  registry.py
  schemas.py
  loader.py

app/context/
  builder.py
  retriever.py
  compression.py
```

Prompt Registry 管：

- `prompt_key`
- `version`
- `agent_name`
- `skill_key`
- `locale`
- `model_family`
- `template`
- `input_schema`
- `output_schema`
- `status`
- `tags`

Skill Registry 管：

- 技能名称，例如 `novel_to_episode_script`
- 技能版本
- 输入/输出 Schema
- 使用哪些 Prompt
- 需要哪些上下文
- 使用哪个模型策略
- 质量检查规则
- 示例 few-shot

Context Builder 管：

- 当前剧本要求
- 整剧设定
- 已确认角色
- 已确认场景
- 已确认道具
- 已确认视觉风格
- 前后集剧情
- 当前分镜附近上下文
- 长篇小说检索片段
- 历史生成结果

交付结果：

- 新增 Prompt/Skill 管理表。
- 每次 AI 调用都有完整快照。
- Agent 不直接拼大段 Prompt，而是调用 Prompt/Context 服务。

验收标准：

- 可以查看一次 AI 调用用了哪个 Prompt 版本。
- 可以回滚 Prompt 版本。
- 可以比较不同 Prompt 的效果、成本和失败率。

## 迭代 3：短期记忆与长期记忆

目标：让系统知道“当前任务做到哪了”，也知道“这部剧长期设定是什么”。

短期记忆用于工作流执行：

- 当前 Workflow 状态。
- 当前步骤输入/输出。
- 当前剧本版本。
- 当前 Agent 决策。
- 用户审核意见。
- 失败重试位置。
- 已生成但未确认的中间结果。

长期记忆用于整部剧一致性：

- 小说章节切片。
- 章节摘要。
- 整剧世界观。
- 角色关系。
- 时间线。
- 角色口癖、动机、禁忌。
- 视觉风格 Bible。
- 声音 Bible。
- 音乐 Bible。
- 已确认图片、视频、声音资产。
- 历史 Prompt 成功/失败记录。

建议存储方式：

| 记忆类型 | 存储 |
|---|---|
| 工作流短期状态 | MySQL + LangGraph checkpoint |
| 结构化设定 | MySQL |
| 小说原文/长文本检索 | Qdrant 或 Chroma |
| 图片/视频/音频资产 | 本地存储先保留，后续 MinIO/S3 |
| Prompt/Agent 运行快照 | MySQL + Langfuse 可选 |

交付结果：

- 小说不再只截断前 2000 字处理。
- 可按角色、剧情、章节、分镜检索上下文。
- 后续生成分镜/视频/声音时能参考整剧设定。

验收标准：

- 长篇小说导入后，能按章节检索相关内容。
- 第 20 集生成时仍能引用第 1 集设定。
- 角色外貌、称呼、关系、声音风格保持一致。

## 迭代 4：任务队列与工作流编排

目标：把当前进程内线程任务升级成可恢复、可重试、可观察的任务系统。

建议引入：

- Redis：任务状态、限流、锁。
- Dramatiq：Python 后台任务队列。
- LangGraph：AI 工作流状态机。
- MySQL：长期任务记录和业务状态。

任务分层：

```text
Workflow Run
  Step 1: 需求分析
  Step 2: 剧本生成/小说改编
  Step 3: 角色提取
  Step 4: 场景提取
  Step 5: 道具提取
  Step 6: 文生图 Prompt
  Step 7: 分镜脚本
  Step 8: 图生视频 Prompt
  Step 9: 角色声音/BGM
  Step 10: 图片/视频/音频生成
  Step 11: 合成导出
  Step 12: QA 检查
```

任务能力：

- 暂停
- 恢复
- 重试某一步
- 跳过某一步
- 人工审核
- 失败续跑
- 并发控制
- 按供应商限流
- 成本统计

交付结果：

- 新增 `workflow_runs`、`workflow_steps`、`agent_runs`。
- 原有图片、视频、分镜、音频任务逐步迁移到队列。
- 前端可以看到完整流水线进度。

验收标准：

- 后端重启后任务能恢复。
- 某一步失败后可以只重试该步骤。
- 取消任务不是只改 DB 状态，而是能让 Worker 停止后续动作。

## 迭代 5：Multi-Agent 体系

目标：不是为了“炫 Agent”，而是把不同创作职责拆开，降低单个大 Prompt 失控风险。

建议采用“监督者 + 专家 Agent”，不要使用完全自由对话式 Agent 群。

Agent 划分：

| Agent | 职责 |
|---|---|
| Producer Agent | 总控，拆任务，决定是否进入人工审核 |
| Requirement Agent | 理解原创剧本要求或小说改编要求 |
| Novel Adapter Agent | 章节解析、摘要、原著设定提取、改编计划 |
| Script Writer Agent | 生成整剧大纲、单集剧本 |
| Continuity Agent | 检查人物、时间线、设定一致性 |
| Character Agent | 提取/补全角色人设、外貌、关系 |
| Scene Agent | 提取场景、空间风格、时代背景 |
| Prop Agent | 提取关键道具 |
| Visual Director Agent | 生成角色/场景/道具文生图 Prompt |
| Storyboard Director Agent | 生成分镜脚本 |
| Video Director Agent | 生成图生视频 Prompt、镜头运动、时长 |
| Voice Agent | 生成角色声音提示词、TTS 参数 |
| Music Director Agent | 生成整剧 BGM 风格、单场景音乐 Cue |
| QA Agent | 检查结构、连续性、画面一致性、敏感内容、缺失字段 |

交付结果：

- 每个 Agent 都通过 Skill + Prompt Registry 运行。
- 每次运行都有输入、输出、模型、成本、耗时记录。
- Producer Agent 不直接写内容，只负责调度和决策。

验收标准：

- 可以单独重跑角色提取，而不重写剧本。
- 可以单独重跑视频 Prompt，而不重生分镜。
- QA Agent 能发现角色名不一致、场景缺失、分镜数量不符等问题。

## 迭代 6：剧本到分镜的完整创作链路

目标：把两类入口统一接到同一条后处理流水线。

完整流程：

```text
AI 原创剧本 / 小说导入改编
  -> 整剧 Bible
  -> 单集剧本
  -> 角色/场景/道具提取
  -> 角色/场景/道具图像 Prompt
  -> 分镜脚本
  -> 首帧/关键帧/尾帧 Prompt
  -> 图生视频 Prompt
  -> 声音 Prompt / BGM Cue
  -> 图片生成
  -> 视频生成
  -> 配音/BGM/字幕
  -> 合成导出
  -> QA 报告
```

原创剧本重点：

- 剧本要求要更完整。
- 先生成整剧设定，再生成单集。
- 每集要有开头钩子、冲突推进、反转、结尾悬念。
- QA 要检查短视频节奏。

小说改编重点：

- 先建立小说长期记忆。
- 先做改编策略，再写剧本。
- 标记哪些剧情保留、合并、删减、重排。
- QA 要检查是否偏离原著设定。

交付结果：

- 两条入口，共用下游资产生成链路。
- 每个阶段产物可编辑、可审核、可重跑。

验收标准：

- AI 原创可以从一句需求走到分镜。
- 小说导入可以从章节走到剧本。
- 用户修改角色后，下游 Prompt 能重新生成并继承修改。

## 迭代 7：声音与音乐系统

目标：把角色声音和整剧音乐纳入一致性管理，而不是最后临时生成。

角色声音要根据整部剧的人设生成，这个是应该做的。否则短剧会出现“人物外貌一致，但声音性格不一致”的问题。

新增数据：

- `character_voice_profiles`
- `music_bibles`
- `music_cues`
- `audio_generations`

角色声音字段：

- 年龄感
- 性别/中性表达
- 音色
- 语速
- 情绪范围
- 口癖
- 台词风格
- 参考音频
- TTS provider
- voice_id
- 禁止项，例如不能太机械、不能过度夸张

音乐 Bible 字段：

- 整剧音乐风格
- 主题旋律方向
- 乐器
- BPM 范围
- 情绪标签
- 高潮/反转/悬疑/温情 Cue
- 每集片头片尾风格
- 音量混合规则

交付结果：

- 生成角色时同步生成声音建议。
- 生成分镜时同步生成音乐 Cue。
- 合成阶段能根据对白、旁白、BGM 做基础混音。

验收标准：

- 同一角色跨集声音一致。
- 不同角色声音可区分。
- 悬疑、反转、告白、冲突场景有不同音乐 Cue。

## 迭代 8：质量评估、成本控制与生产化

目标：让系统可长期迭代，而不是“能跑一次”。

质量评估：

- 剧本结构完整性。
- 人物一致性。
- 场景连续性。
- 分镜数量和时长。
- Prompt 是否缺少主体、动作、镜头、风格。
- 视频 Prompt 是否可执行。
- 声音是否符合人设。
- BGM 是否压过对白。
- 敏感内容检查。
- 成本和耗时统计。

成本控制：

- 低成本模型做摘要、提取、检查。
- 高质量模型做剧本、分镜、关键 Prompt。
- 图片/视频生成前必须经过结构检查。
- 重试要有上限。
- 同一素材支持缓存和版本复用。

交付结果：

- 每次生成有质量报告。
- 每部剧有成本统计。
- 可以比较不同 Prompt、不同模型、不同 Agent 版本效果。

验收标准：

- 能知道一部剧从导入到成片花了多少钱。
- 能定位失败最多的是哪个 Agent 或供应商。
- 能回滚某个 Prompt/Skill 版本。

## 推荐实施顺序

第一阶段先做底座，周期大约 1-2 周：

1. 安全配置、日志、错误码。
2. Pydantic Schema。
3. Prompt Run 记录。
4. 任务表增强。

第二阶段做可编排流水线，周期大约 2-4 周：

1. Redis + Dramatiq。
2. Workflow Run / Step。
3. 原创剧本 Workflow。
4. 小说改编 Workflow。
5. 失败重试、恢复、取消。

第三阶段做 Agent 化，周期大约 3-5 周：

1. Skill Registry。
2. Prompt Registry。
3. Context Builder。
4. Script / Novel / Character / Scene / Prop Agent。
5. Storyboard / Visual / Video Agent。
6. QA Agent。

第四阶段做长期记忆和一致性，周期大约 3-5 周：

1. 小说切片和向量检索。
2. Drama Bible。
3. Character Bible。
4. Visual Bible。
5. Voice Bible。
6. Music Bible。

第五阶段做成片生产链路，周期大约 4-8 周：

1. 文生图资产版本管理。
2. 图生视频任务编排。
3. TTS 配音。
4. BGM Cue。
5. 字幕。
6. 视频合成。
7. QA 报告。
8. 成本统计。

## 最终建议

短期不要先重写全部服务。最好的升级路径是：

先把 `Prompt + Context + Task + Run Log` 四个底座抽出来，再接 `Memory`，最后引入 Multi-Agent。这样现有角色、场景、道具、分镜、图片、视频能力都能逐步迁移，不会因为一次大改把已有功能打散。

第一批真正值得落地的改造 PR 可以这样拆：

1. `config/security/logging` 安全和日志底座。
2. `schemas` 剧本/角色/场景/道具/分镜结构化模型。
3. `prompt_runs` AI 调用快照记录。
4. `workflow_runs` 工作流运行记录。
5. `dramatiq redis worker` 后台任务替换线程池。
6. `context_builder` 上下文统一构建。
7. `skill_registry` 技能注册。
8. `original_script_workflow` AI 原创剧本流程。
9. `novel_adaptation_workflow` 小说改编流程。
10. `voice_music_workflow` 角色声音和背景音乐流程。

这条路线的重点是：每一轮都能交付可用能力，而不是等半年后才看到一个“新架构”。
