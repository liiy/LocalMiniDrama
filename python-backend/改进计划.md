每个迭代都按下面约定实施，避免 LangGraph、任务队列、Agent 框架职责重叠。

## 技术栈基线

| 层级 | 约定技术 | 职责 |
|---|---|---|
| API | Python 3.12、FastAPI、Pydantic v2 | REST API、参数校验、OpenAPI |
| 数据库 | MySQL 8、SQLAlchemy 2、Alembic | 业务数据、版本、运行记录、迁移 |
| 后台任务 | Redis 7、Dramatiq | 图片、视频、音频等长任务执行 |
| AI 编排 | LangGraph | 工作流状态机、Agent 调度、暂停恢复、人工审核 |
| Agent 契约 | 自研 `BaseAgent` + Pydantic Schema | 保持多模型兼容，不引入第二套编排框架 |
| Prompt | Jinja2、MySQL Prompt Registry | 模板渲染、版本管理、灰度和回滚 |
| Skill | Python Registry + Pydantic + MySQL | 技能声明、版本、输入输出、模型策略 |
| 长期记忆 | LlamaIndex、Qdrant | 小说切片、语义检索、上下文召回 |
| 短期记忆 | Redis + MySQL Snapshot | 当前步骤状态、重试点、审核意见 |
| 文件存储 | 本地 Storage Adapter、MinIO/S3 | 图片、视频、声音、导出文件 |
| 模型接入 | HTTPX + 现有 Provider Adapter | 文本、图片、视频、TTS 多供应商接入 |
| 视频音频 | FFmpeg CLI | 转码、字幕、配音、BGM、合成 |
| 可观测性 | OpenTelemetry、Langfuse、Prometheus | 链路、Prompt、Token、成本、任务指标 |
| 测试质量 | pytest、pytest-cov、Ruff、mypy | 单测、契约测试、静态检查 |
| 部署 | Docker Compose | MySQL、Redis、Qdrant、MinIO、应用服务 |

关键约定：

- MySQL 是业务数据和任务状态的最终数据源。
- Redis 只用于队列、锁、限流和短期状态，不保存唯一业务数据。
- Dramatiq 负责“执行任务”，LangGraph 负责“决定执行什么”。
- LangGraph 不直接承担视频生成等耗时 Worker。
- Qdrant 只存向量和检索元数据，原文及结构化事实仍存 MySQL/对象存储。
- Prompt 集中管理；Agent 只声明 Prompt Key 和上下文需求。
- 当前不引入 OpenAI Agents SDK，避免限制多供应商能力。
- 当前不引入 Celery；第一阶段统一使用 Dramatiq，降低部署和维护复杂度。

## 总体技术路径

```text
FastAPI API
  -> Application Service
  -> MySQL workflow_run
  -> Dramatiq Task
  -> LangGraph Workflow
  -> Specialist Agent
  -> Skill Registry
  -> Prompt Registry + Jinja2
  -> Context Builder
  -> MySQL + Redis + Qdrant
  -> Text/Image/Video/TTS Provider
  -> MinIO/Local Storage
  -> FFmpeg
  -> Langfuse + OpenTelemetry
```

## 迭代 0：安全与工程底座

技术栈：

- FastAPI Middleware
- `pydantic-settings`
- PyJWT/现有 Token 鉴权
- `cryptography` Fernet
- Pillow
- 结构化 JSON Logging

技术路径：

- YAML 只保存非敏感默认值和环境变量占位符。
- 数据库密码、API Token 通过环境变量注入。
- AI Key 使用 Fernet 加密后存入 MySQL，主密钥来自 `LMD_MASTER_KEY`。
- API 响应统一脱敏。
- 请求注入 `request_id`，日志自动隐藏密码、Token、Authorization。
- 上传进行扩展名、MIME、文件头、大小、路径联合校验。
- 本地模式允许关闭鉴权，部署模式启动时强制检查 Token 和主密钥。

完成门槛：

- 无明文数据库密码和 AI Key。
- 上传不能越过 storage 根目录。
- API 错误响应和日志均包含请求 ID。
- 安全相关测试通过。

## 迭代 1：结构化数据模型与创作标准

技术栈：

- Pydantic v2
- JSON Schema
- SQLAlchemy 2
- Alembic
- pytest

当前项目已经出现 `app/schemas/`，因此技术路径不是再创建一套，而是先审计、修复并正式接入。

需要统一的模型：

- `ScriptSpec`
- `NovelAdaptationSpec`
- `DramaBible`
- `EpisodeScript`
- `CharacterProfile`
- `SceneProfile`
- `PropProfile`
- `StoryboardShot`
- `VisualPrompt`
- `VideoPrompt`
- `VoiceProfile`
- `MusicBible`
- `MusicCue`

技术路径：

1. 修复现有 Schema 的乱码、字段约束、默认值和命名。
2. 建立公共 `SchemaBaseModel`，统一 `extra="forbid"`、时间格式和序列化规则。
3. 增加原创剧本、小说改编两种请求模型。
4. 增加 AI 输出解析器，将模型返回转换为 Pydantic 对象。
5. 增加 JSON 修复，但修复后必须再次进行 Schema 验证。
6. 建立 `schema_version`，生成产物记录所使用的 Schema 版本。
7. 先增加 `/api/v1/schemas/*/validate` 校验接口。
8. 再逐步替换现有 `payload: dict`，不一次性破坏旧 API。

完成门槛：

- 两种剧本入口都有严格 Schema。
- 非法集数、镜头时长、空角色名等在进入 AI 前被拒绝。
- AI JSON 输出必须经过 Pydantic 验证。
- 原接口契约测试继续通过。

## 迭代 2：Prompt、Skill、Context 中心

技术栈：

- Jinja2
- Pydantic
- SQLAlchemy/Alembic
- MySQL
- SemVer 版本规则

模块约定：

```text
app/prompts/
app/skills/
app/context/
```

技术路径：

- `prompt_templates` 保存 Prompt 标识和归属。
- `prompt_versions` 保存不可变模板版本。
- `skills` 保存技能定义，`skill_versions` 保存版本快照。
- Skill 定义输入 Schema、输出 Schema、Prompt Key、模型策略、上下文策略和质量规则。
- Context Builder 根据 `drama_id/episode_id/storyboard_id` 构建上下文。
- 每次 AI 调用生成 `prompt_run`，记录最终 Prompt、版本、上下文引用、模型、Token 和耗时。

完成门槛：

- Prompt 可发布、停用、回滚。
- Agent 代码中不再出现大段业务 Prompt。
- 同一次生成可以完整复现其 Prompt 和上下文。

## 迭代 3：短期与长期记忆

技术栈：

- Redis
- MySQL
- Qdrant
- LlamaIndex
- 统一 Embedding Provider

技术路径：

- Redis 保存当前 Workflow 热状态、临时上下文和取消标记。
- MySQL 保存 `context_snapshots` 和最终确认事实。
- 小说按章节、场景和语义段落切片，写入 `novel_chunks`。
- LlamaIndex负责解析、切片和检索流程。
- Qdrant 保存小说、剧情、角色关系、历史分镜的向量。
- Drama Bible、Character Bible、Visual Bible、Voice Bible、Music Bible 作为长期记忆。
- 检索结果先重排、去重、压缩，再交给 Agent，禁止直接塞入整本小说。

完成门槛：

- 长篇小说不再截断到固定字符数。
- 后续集数能检索前面剧情和角色设定。
- 用户确认的信息优先于 AI 历史结果。
- 所有上下文都能追溯来源。

## 迭代 4：任务队列与工作流编排

技术栈：

- Dramatiq
- Redis Broker
- LangGraph
- MySQL
- Server-Sent Events 或 WebSocket

技术路径：

- `workflow_runs` 表示整条创作流水线。
- `workflow_steps` 表示单个步骤。
- LangGraph 描述步骤依赖、条件分支、人工审核节点。
- Dramatiq Worker 执行文本、图片、视频、TTS、合成任务。
- 按 `text/image/video/audio/merge` 建立独立队列。
- 增加幂等键、心跳、超时、指数退避、供应商限流、取消检查。
- 前端通过 SSE 接收任务进度，查询接口作为兜底。

完成门槛：

- 服务重启后任务可恢复。
- 可以暂停、继续、取消、重试单个步骤。
- 同一幂等请求不会重复生成和扣费。

## 迭代 5：Multi-Agent

技术栈：

- LangGraph
- 自研 `BaseAgent`
- Pydantic Schema
- Skill Registry
- Context Builder

Agent 约定：

- Producer/Supervisor
- Requirement
- Novel Adapter
- Script Writer
- Continuity
- Character
- Scene
- Prop
- Visual Director
- Storyboard Director
- Video Director
- Voice
- Music Director
- QA

技术路径：

- 每个 Agent 是 LangGraph Node。
- Agent 本身不直接访问数据库，通过 Repository/Tool 接口调用。
- Agent 不持有永久私有记忆，由 Context Builder 注入。
- Supervisor 只调度，不直接生成全部业务内容。
- QA Agent 输出结构化问题清单，不直接覆盖正式内容。
- 重要节点进入 Human-in-the-loop 审核。

完成门槛：

- 角色提取、分镜或视频 Prompt 可独立重跑。
- Agent 输入、输出、模型、Skill、Prompt 均可审计。
- 任一 Agent 失败不会导致整条剧本重新生成。

## 迭代 6：剧本到视频完整链路

技术栈：

- LangGraph
- Dramatiq
- 现有 AI Provider Adapter
- HTTPX
- MinIO/S3
- FFmpeg

技术路径：

```text
原创/小说
-> Drama Bible
-> 分集剧本
-> 角色/场景/道具
-> 文生图 Prompt
-> 分镜
-> 首帧/关键帧/尾帧
-> 图生视频 Prompt
-> 图片和视频生成
-> 合成
```

- 将现有 `imageClient.py`、`videoClient.py` 拆成统一 Provider Protocol。
- 本地存储先实现 `StorageBackend`，生产环境切到 MinIO。
- 素材引入版本号和派生关系。
- 修改角色设定后，只标记相关下游资产失效，不重跑全部项目。

完成门槛：

- 两类剧本入口共用下游流水线。
- 每个阶段都可编辑、审核、回滚和定向重生成。

## 迭代 7：角色声音与整剧音乐

技术栈：

- 现有 TTS Adapter
- 新增 Music Provider Adapter
- Dramatiq
- FFmpeg
- `pyloudnorm` 可选用于响度分析

技术路径：

- 角色生成后建立 `VoiceProfile`。
- 保存 `voice_id`、参考音频、语速、音高、情绪规则和禁用特征。
- Drama Bible 同步生成 Music Bible。
- 分镜生成时建立 `MusicCue` 和 `SFX Cue`。
- TTS 按对白逐段生成，保存时间轴和角色映射。
- FFmpeg 完成对白、旁白、BGM、音效、字幕混合。
- 统一目标响度，避免 BGM 压住对白。

完成门槛：

- 同一角色跨集声音一致。
- 不同角色具备可辨识性。
- BGM 可以按剧情转折自动切换且不覆盖对白。

- Langfuse
